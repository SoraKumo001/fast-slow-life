# Phase 3 仕様 ― 経済v2「循環する経済」（価格と財布の実装）

前提: Phase 2 完了（commit `6ba8ccb` push 済み）。Phase 3 は v2 で初めて**ゲームロジックとセーブ形状を変更する**フェーズである。
目的: 町の金の流れを「自動で一方向に吸い上げる仕組み」から「価格があり、財布の間で回る仕組み」に変える。

## 1. 現行経済の実態（コード確認済み）

- 採取物は村人の `pool`（仮置き場）に入り、`poolPurchase.ts` が**全量を basePrice で自動買取**する。プレイヤー金（`state.gold`）は不足しても減り続け、予算の概念がない。買った品はプレイヤー在庫に入る
- 食料代（`survival.ts`、日次）: 村人がプレイヤーへ一律に支払う。Buff 料理は basePrice、無Buffは一律 2G、飢餓は 0。価格は固定
- クラフト完成品は無償でプレイヤー在庫に入る。職人への対価はない（報奨金 `payVillagerReward` はプレイヤーの手動操作のみ）
- キャラバン（輸出入）が唯一の対外フロー。市のトレンドは自動売買ルール側にある
- 計画書にあった「ツケ／借金デバフ 0.7×」は現行コードに存在しない（ドキュメント上のみ）。本フェーズの対象外とする

## 2. Phase 3 の範囲

やること:
1. **市場価格**: アイテムごとに在庫量で変動する価格を持つ（§3）
2. **買取の価格・予算制**: プール買取を市場価格×予算制限に変える（§4）
3. **食料代の価格連動**: Buff 料理の食料代を市場価格にする（§5）
4. **クラフト賃金**: 完成時に金庫から職人へ賃金を払う（§6）
5. **価格方針（条例）**: プレイヤーが価格水準を3段階で選べる（§7）
6. **夕方の精算**: 日次の収支サマリをログと画面に出す（§8）
7. **セーブ移行**: SAVE_VERSION 7 → 8（§9）

やらないこと（後続フェーズへ）:
- 需要ボード（プレイヤーが「パン10個求む」と掲示する仕組み）→ Phase 5 で生活UIと一緒に
- キャラバンの再設計（現行のまま。対外フローとして存続）
- 村人の裁量買い物（装備・嗜好品）。Phase 2 の「買い物ぶらぶら」は見た目のまま
- 在庫の分割（店在庫と倉庫在庫の分離）。市場は既存のプレイヤー在庫に対する価格・会計レイヤーとして実装する

## 3. 市場価格（新規: `src/store/market.ts`、純関数）

新規の保存フィールド（§9）:
- `marketPrices: Record<string, number>` ― アイテムID → 現在価格（整数G）
- `pricePolicy: "cheap" | "standard" | "premium"` ― 価格方針（初期値 standard）

価格の決定（純関数 `computeMarketPrice(item, stock, policy): number`）:
- 目標在庫 `targetStock(item)`: 食料（food 系）= 20、素材 = 30、その他 = 10。交易所レベルで +5/レベル（Lv1 なら上記そのままではなく +5。実装時にカテゴリ判定は既存の item.category / type を使う）
- 希少度係数 `factor = clamp(1 + (target - stock) / target, 0.4, 1.6)`（在庫0で 1.6、目標どおりで 1.0、2倍で 0.4）
- 方針倍率: cheap ×0.8 / standard ×1.0 / premium ×1.25
- 価格 = `max(1, round(basePrice × factor × policyMul))`。basePrice が 0 のアイテムは価格を持たない（買取対象外、現行どおり）
- 再計算タイミング: 日境界（新しい日の処理）で全アイテム分を再計算して `marketPrices` を差し替える。日中は固定（1時間ごとの価格変動はしない）

テスト: 在庫に対する単調性（在庫が増えると価格は下がる）、クランプ境界、方針倍率、basePrice 0 の除外、決定性。

## 4. 買取の変更（`poolPurchase.ts` を改修）

- 単価 = `marketPrices[itemId]`（なければ basePrice にフォールバック）
- **予算制限**: 金庫（state.gold）が払える範囲だけ買う。アイテム単位で買える個数 = `min(所持数, floor(gold / 単価))`。買えなかった分は pool に残る（消えない）
- 買取ログは現行の文面形式を維持しつつ単価と合計を出す。残った場合は「金庫不足のため一部買取できませんでした」の要約ログを1日1回まで
- 呼び出し位置（パイプライン内の順序）は現行のまま変えない
- RunStats の `totalItemsPurchased / totalGoldFromPurchases` は新価格で集計する

## 5. 食料代の価格連動（`survival.ts` を改修）

- Buff 料理の食料代 = `marketPrices[activeFoodBuffId]`（なければ basePrice、現行フォールバック）
- 無Buffの一律 2G と飢餓 0 は現行のまま（配給の最低価格として残す）
- 「払える額だけ徴収する」現行の修正（B2）は維持する。金は村人→金庫への移転であり、生成・消失させない

## 6. クラフト賃金（`crafting.ts` の完成パスを改修）

- クラフトジョブが完成したとき、担当村人へ賃金 = `max(1, round(完成品 basePrice × 0.2))` を金庫から支払う
- 金庫が不足する場合は払える分だけ払い、不足はログに残す（村人の金はマイナスにしない、金庫もマイナスにしない）
- 訓練・アップグレードへの賃金は本フェーズでは付けない（訓練は現行の goldPerHour の流れを維持）
- ログ: 「◯◯ にクラフト賃金 X G を支払いました」系の文面で、既存ログ形式に合わせる

## 7. 価格方針のUI

- 施設タブの交易所（market）カード内に、価格方針の3ボタン（安売り／標準／高級）を置く。切替は即時に保存され、翌日の価格再計算から効く（当日の価格は変えない）
- あわせて §8 の「昨日の精算」を同じカード内に小さく表示する
- 既存の FacilityList の構造に収めること。新規タブは作らない。classic 表示でも同じカードが使われるなら追加UIは両方に出てよい（経済は共通ロジックのため）

## 8. 夕方の精算

- 日境界で、その日の内部フローを集計してログに1件出す:
「◯日目: 買取 -X G / 食料代 +Y G / 賃金 -Z G / キャラバン ±W G」
- 集計のために、その日のフローを貯める仕組みを実装する。既存の RunStats は累計専用なので、日次分はパイプラインのアキュムレータか新規フィールド `lastSettlement: { day, poolPurchase, foodIncome, craftWages, caravanNet} | null` に**最新分だけ**持つ（履歴は持たない）
- キャラバンの日次ネットは既存の caravan 処理の gold 変化から取る。取りにくい場合は caravanNet を 0 ではなく「含まない」設計にせず、economy フェーズ前後の gold 差分で近似してよい（その旨をコードコメントに明記）

## 9. セーブ移行

- SAVE_VERSION を 7 → 8 に上げる。既存のマイグレーション機構（persistence.ts のバージョンループ）に v7→v8 を追加: `marketPrices = {}`（初回日境界で計算される）、`pricePolicy = "standard"`、`lastSettlement = null`
- initialState にも同初期値を入れる
- pool・村人 gold・プレイヤー gold の既存値はそのまま引き継ぐ（リセットしない）

## 10. 金の保存則（不変条件）

内部フロー（買取・食料代・賃金）はすべて**移転**であり、金の総量（金庫＋全村人の gold 合計）を変えない。総量が変わるのは対外フローだけ: キャラバン輸出入、施設アップグレード費、雇用費、訓練費、報奨金など既存の出入り（現行のまま）。
この保存則をテストで固定する: キャラバン等を止めた固定シナリオで1日を回し、総量が一致すること。

## 11. ゲート

1. `pnpm build` 成功
2. `pnpm test:run` 全緑。価格変更で既存テスト（poolPurchase / survival / crafting / persistence / gameLoop 等）の期待値が変わる場合は、新仕様に沿って更新してよい。ただし**テスト件数を減らさない**ことと、保存則テスト（§10）と価格テスト（§3）を新規に追加すること
3. `pnpm test:balance`（30日バランスシミュレーション）が通ること。デフォルト戦略で破産ゲームオーバーにならず、30日目の金庫残高と村人の平均所持金をレポートに含めること。現行（Phase 2 時点）の同シミュレーション結果と比較し、大きく悪化していたら数値を報告して判断を仰ぐ（勝手に価格式を緩めない）
4. 変更ファイルは経済まわり＋型＋永続化＋FacilityList の交易所カードに限ること。ダンジョン・戦闘・生活AI（Phase 2 のファイル）には触らない
5. スクリーンショット: 交易所カードに価格方針ボタンと昨日の精算が見えること。可能なら村人の所持金が買取・賃金で動いたことがログから読める場面
