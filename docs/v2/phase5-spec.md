# Phase 5 仕様 ― 統合・仕上げ（需要ボード／バランス再調整／旧レイアウト／リリース整備）

前提: Phase 4 完了（commit `ba194c0` push 済み）。v2 リニューアルの最終フェーズ。
やることは4つ: (1) Phase 3 から先送りした需要ボード、(2) pool 修正と襲撃導入で易しくなりすぎたバランスの再調整、(3) 旧レイアウトの扱いの確定、(4) リリース整備。

## 1. 現行コードの実態（確認済み）

- 目標個数システムは既にある: `targetAmounts`（アイテムごとの目標在庫数）を `InventoryPanel` / `ItemTradeSettings` で編集でき、在庫UIに未達バッジも出る。ただし価格には一切連動していない
- 価格は Phase 3 の `market.ts`（希少性係数 × 方針倍率、日次再計算）
- バランス現状（シミュレーション30回、自動戦略）: 通常戦略クリア 100% / 破産 0%、全Buff クリア 96.7%。Phase 4a の pool 修正（即時買取の廃止）前は通常クリア 10% / 破産 47% で、こちらは買取バグ由来の理不尽な難しさだった
- `pnpm test:balance` は出荷状態では動かない（vitest の include から `scripts/` が外れている）

## 2. 需要ボード

### 2.1 価格への需要係数（`market.ts`）

- プレイヤーが目標を設定したアイテム（target > 0）にだけ需要係数を掛ける:
  - 不足率 = clamp(1 − 在庫 / 目標, 0, 1)
  - 需要係数 = 1 + 0.3 × 不足率（最大 ×1.3、在庫が目標以上なら ×1.0、下げ方向には働かせない）
- 係数は日次再計算に組み込む。`marketPrices` の消費側（買取・食料代）は無変更でよい
- お金の保存則テスト（moneyConservation）が引き続き緑であること

### 2.2 ボードUI

- `InventoryPanel` の上部に「需要ボード」セクションを新設する: 目標設定済みアイテムを不足の大きい順に並べ、在庫/目標、不足数、現在価格（需要係数込み）と ↑ 表示を出す。目標の編集は既存の `ItemTradeSettings` をそのまま使う（導線だけ追加）
- 町の広場に掲示板を置く（`GameTownViewport`）: 広場をクリックしたときのミニカードに「需要不足トップ3」を表示し、在庫タブへ開くボタンを付ける。掲示板の 3D メッシュは小さな板＋屋根程度の最小構成でよい
- 自動派遣が目標個数を既に重み付けしている場合はそのまま。していない場合、本フェーズでは重み付け追加はしない（ボードは価格と可視化まで）

## 3. バランス再調整

### 3.1 目標帯（自動戦略シミュレーション30回 × 2戦略）

| 指標 | 目標 |
|---|---|
| 通常戦略 クリア率 | 30〜60% |
| 通常戦略 破産率 | 20% 以下 |
| 全Buff戦略 クリア率 | 70〜90% |
| 襲撃の発生（通常戦略のランに占める割合） | 30% 以上（脅威の圧が存在すること） |
| 通常戦略 平均クリア日数 | 15日以上（速攻で終わらないこと） |

### 3.2 調整レバー（優先順。この順に1グループずつ変えてシミュレーションを回す）

1. 脅威度: `THREAT_BASE_RATE_PER_HOUR` / 加速指数（襲撃頻度と圧）
2. 市場: 希少性の目標在庫・クランプ幅（0.4〜1.6）
3. 食料まわり: 配給・Buff 食の価格に効く市場パラメータ側（式は変えない）
4. データ: 施設の強化コスト、初期ゴールド
5. モンスターのステータス（データ）: 1〜4で届かない場合のみ使い、使ったら報告書で目立つように明記する

戦闘・採取の**計算式**は変更しない。変えてよいのは定数とデータだけである。

### 3.3 手順と停止条件

- 1イテレーション = レバー1グループ変更 → シミュレーション30回×2戦略 → 数値を記録。最大5イテレーション
- 目標帯に入ったら止める。5回で届かなければ最も近い設定で止め、届かなかった指標と理由を報告する（勝手に目標帯を広げない）
- `pnpm test:balance` を正式に直す: `scripts/` を含む専用 vitest 設定をコミットし、スクリプトがそのまま動くようにする。シミュレーション側のアサーションは §3.1 の目標帯に合わせる
- 最後にバランススイートを3回連続で回し、3回とも合格することを確認する（確率のブレで緑になる構成は不可）

## 4. 旧レイアウトの扱い

- `?prototype=town`（Phase 0 の開発用プロトタイプ）は**撤去**する: ルート分岐、`TownPrototypePage`、プロトタイプ専用モジュール（`prototypeAgents` 等。他から使われているモジュールは残すこと。削除前に import を確認する）
- `?classic=1`（旧4カラム）は**非推奨の逃げ道として残す**: Phases 2〜4 の変更で壊れていないか実際に開いて確認し（スクリーンショット＋タブ一巡）、軽微な破損は直す。大きな破損があれば直さずに報告して止まる
- README に classic の非推奨を明記する
